# 逆向工程总结

## 已经理解

| 模块 | 证据级别 |
|---|---|
| 首屏资源结构（457 请求 / 22 MB / 99% 在首屏） | 实测 |
| 虚拟列表（滚动不增 DOM、不增请求） | 实测 |
| 播放器分片（player-0..5 + pre-build-xgplayer，约 1.5 MB 可测） | 实测 + 静态 |
| 上报独立文件（collect.dy.js 186 KB + mcs 32 次） | 实测 |
| 无 sourcemap（全部样本） | 实测 |
| feed 预取 9.4 MB | 实测 |

## 尚未理解

- 151 个无体积 script 的作用
- chunk 之间的真实依赖图（需 hook 打包器，未做）
- 广告/推广/短剧/AI 模块具体落在哪个 chunk（关键词法不可靠）
- 风控相关（pylon-wasm 1.1 MB）的实际职责

## 可安全优化（有证据）

- 我们自己的层：导航隐藏（已做）、启动器死代码（已做）、脚本频率（已有守卫）
- 页面层：**没有**任何一项拿到安全证据

## 不应触碰

- 任何 `player-*` / feed / collect / wasm
- 路由与播放器初始化
- 登录、风控、验证码相关（2 个 iframe）

## 预计收益与验证方式

| 方向 | 现实收益 | 怎么验 |
|---|---|---|
| 页面层瘦身 | **未知**（拿不到"停用后仍正常"的证据） | 单 chunk 阻断 + 全功能回归，成本高 |
| 内存 | **无**（增长在 Chromium 侧，与我们的代码无关） | 已多次实测 |
| 启动 | 可能有（少加载若干 chunk） | 冷启动耗时前后对比，需先能定位可延迟的 chunk |

## 最小风险实施顺序（如果继续）

1. 先用 CDP `Network.setBlockedURLs` 在**独立实例**里逐个阻断可疑 chunk，观察页面是否正常（每组一次，可回滚）
2. 只对"阻断后功能完全正常"的 chunk 做正式拦截
3. 每次只改一项，记录前后数据

## 结论

**本轮没有发现可以安全瘦身的页面层目标。** 首屏 22 MB / 457 请求是抖音前端的既定行为，其中 9.4 MB 是内容数据、1.5 MB 是播放器、其余是框架与资源。真正的内存问题在 Chromium 侧（已有定性），不在这些 bundle 的"多余功能"上。

如果目标是"轻量化"，**投入产出比最高的仍然是**：定期刷新回收内存 + 保持我们自己的脚本不做无谓工作（已完成两项）。

# 连续切换视频内存增长调查（2026-11-25）

方法：profile 副本 + 独立实例（不碰正式实例），注入全部 9 个 userscript，`mouse.wheel` 连续切换 15 次，`CDP Performance.getMetrics` 每次采样。未强制 GC。

## 2. 曲线形状

```
heap:  89 → 104 → 120 → 121 → 122 → 123 → 125 → 126 → 72 → 73 → 72 → 82 → 170 → 91 → 91 → 92 → 118 → 117
                     ↑ 平台            ↑ GC 回落                          ↑ 突变      ↑ 平台     ↑ 静置回升
nodes: 1993 → 2443 → 2711(稳定到 S11) → 3803 → 3876~3970(稳定)
```

## 3. 三个维度的对比

| 维度 | 表现 | 判断 |
|---|---|---|
| **JS Heap** | 89→126 后**回落到 72**，之后 72–92 波动，静置回升到 117 | **不是线性泄漏**，是「分配→GC」锯齿；S8 的 -54MB 是真实 GC |
| **DOM 节点** | 1993→2711（S2 起稳定），S12 跃到 3803 后稳定 | **不是逐视频累积**，是单次结构变化（videos 从 1 变 3，疑似预加载/浮层容器） |
| **GPU / 进程内存** | **未采集** | 见「未验证」 |

关键反证：如果每切一个视频就泄漏，heap 不会在 S8 掉到 72 MB，节点也不会从 S2 起连续 9 个采样点一动不动。

## 4. 最可能的增长来源（按证据强度）

### ① 媒体解码缓冲与 GPU 缓存（证据：间接，但方向最合理）

`videos` 从 1 变 3、heap 在 S12 冲到 170 MB，都发生在「切换后页面结构变化」的时刻。视频解码的 VideoFrame、解码器实例、GPU 纹理走的是**原生内存**，不计入 JS Heap —— 这正是我这次测不到的部分，也是「JS 堆看着还好、任务管理器却很高」的典型原因。

### ② 常驻定时器持续产生对象（证据：中等）

静态审查：10-frequenk 3 个 `setInterval`、12-douyinplus 4 个、13-smartfeed 2 个，合计约 11 个常驻定时器 + 4 个 `MutationObserver` + 116 处 `addEventListener` 注册点。静置 60 秒 heap 从 92 涨到 118（+26 MB）而节点不变，符合「定时器周期性分配」的特征，但不是无上限增长（否则 S8 不会回落）。

### ③ DOM 节点单次跃升（证据：弱）

1993→3879 是一次性的，之后稳定。不构成持续增长，但会抬高基线约 1800 个节点。

## 5. 仍然无法确认（必须标注）

1. **进程级 Working Set / Private Bytes 曲线** —— 本次探针只在页面内采样，没拿进程内存。
2. **GPU 进程内存** —— 需要 `chrome://gpu` 或外部采样。
3. **EventListeners 计数** —— 本机 CDP 未返回该指标，无法证明监听器是否随切换累积。
4. **正式环境对照** —— 本次是 profile 副本（可能处于未登录/降级状态），与正式实例（25 个进程）条件不同。
5. 15 次切换**没有出现单调增长**，但这**不能否定长时间（上百次）或特定视频类型（直播、长视频）下的累积**。

## 6. 下一步最小验证方案（不改代码、不碰正式环境）

按性价比排序，都能自动化：

1. **A/B 对照（最有力）**：同一份 profile 副本，跑两轮——一轮注入全部 userscripts，一轮**一个都不注入**，同样切 15 次。两轮 heap 曲线之差 = 脚本的真实贡献。这一步能直接把「脚本嫌疑」定量。
2. **补进程内存**：跑切换的同时，外部 PowerShell 每 3 秒采一次 renderer / gpu-process 的 `WorkingSetSize` 与私有字节。若 renderer 单调增而 heap 平 → 原生内存（DOM/解码器）；若 gpu 单调增 → 媒体缓冲。
3. **补监听器计数**：改用 `page.evaluate` 统计 `getEventListeners` 不可用，可由 `Performance.getMetrics` 的 `EventListeners` 在部分版本可用，或改用 CDP `DOMDebugger.getEventListeners`（需节点引用，较重）。
4. 若要做长时间验证：连续切 100 次，观察 heap 是否出现「回落点消失」——那才是泄漏信号。

## 7. 结论

**这次 15 次切换没有观察到「每切一个视频就稳定增加不可回收内存」的现象。** JS 堆有明确的 GC 回落（126→72 MB），DOM 节点在 S2 之后连续 9 次采样不变。增长主要发生在切换瞬间的结构变化（videos 1→3）与静置期间的后台分配（+26 MB）。

你看到的 98%，更可能是**多进程原生内存（媒体缓冲 + GPU）叠加**的瞬时峰值，而不是网页 JS 泄漏；但这部分我这次没采到，属于**未验证**，不能当结论用。要定论就做第 6 节第 1 条那个 A/B 对照。

## 补充：正式实例实测（2026-11-25 17:02–17:06，用户登录态，10 个进程）

外部只读采样，3 秒一个点，共 71 个样本；期间用户手动连续切换 15 个视频。

| 时段 | renderer | gpu | 可用内存 |
|---|---|---|---|
| 17:02:42 基线 | 3456 MB | 593 MB | 4502 MB |
| 17:03:07–17:04:09（切前/初期） | 3323–3577 | 623–640 | 4079–4381 |
| 17:04:21 | 3828 | 839 | 3769 |
| 17:04:34 | **4142** | 739 | 3633 |
| 17:04:59 | 4171 | 610 | 3499 |
| 17:05:11（回落） | 3792 | 564 | 3841 |
| 17:06:14 结束 | **4421** | 636 | 3366 |

统计：renderer 最小 3322 / 最大 4421 / 均值 3783，**+965 MB（15 次切换，约 64 MB/次）**，中途出现一次 -379 MB 的回落。

### 结论（实测）

1. **基线就已经是 3.4 GB** —— 这不是切换造成的，是页面长时间运行累积的结果。browser(235) + gpu(600) + utility(97) + node(265) 合计仅约 1.2 GB。
2. 切 15 个视频再涨约 1 GB，**有回落点**，不是严格单调 —— 符合「媒体缓冲/解码帧按需分配、部分可回收」，而不是 JS 对象泄漏。
3. 与副本实验（heap 仅 90–170 MB、DOM 节点稳定）交叉印证：**3.4–4.4 GB 几乎全是原生内存，不是 JS 堆。**

### 未验证

- 刷新页面后 renderer 是否回落（最快的判定，需用户操作）
- 是否有单个渲染进程之外的解码器进程在分担
- 长时间（上百次切换）是否出现「回落点消失」

### 最小验证

按一次刷新（不清理数据、不退登录），看 renderer 是否掉回 500 MB 以内。掉落 ⇒ 页面累积，非进程泄漏；不掉 ⇒ 需要进一步查解码器/GPU 侧。

## 补充二：50 个视频长跑（2026-11-25 17:57–18:08，真实登录态）

临时探针（10 秒一次，已删除）记录 JS Heap / DOM / video，外部 5 秒采进程内存。

```
JS Heap:   49 → 230~280 平台 → 峰值 476（刷新瞬间）→ 368
DOM 节点:  633 → 2714 → 4119（一次性跃升）→ 4053（连续 4 个采样点不变）
renderer:  1035 → 峰 1440 → 末 1157 MB（来回波动，无单调增长）
刷新后:    nodes 4053 → 2285
```

**结论**：
1. JS Heap 无累积，刷完仅比开始高约 50 MB 且有回落；峰值 476 出现在刷新那一秒，是重建过渡态。
2. DOM 节点是**一次性跃升后稳定**（2756→4010，随后 4 个采样点恒为 4053），非逐视频累积。
3. renderer 无单向增长，末值低于峰值。

**修正**：此前观察到的 renderer 3.4 GB 高位，**用 50 个视频复现不出来**，更像长时间（数小时）运行后的平台值，而不是"每刷一个涨一点"。本项不再作为可优化项。

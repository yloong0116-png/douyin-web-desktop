## 3. 从这组数据能确定的

1. **10.8 分钟内 renderer 单进程从 2.42 GB 涨到 3.61 GB，没有出现回落点。** 前一次（17:02–17:06）15 次手动切换的采样中曾出现 −379 MB 与 −500 MB 的回落；**这次的 10.8 分钟里一次都没出现**。两种可能：① 该时段用户在持续播放/上滑，分配速率高于回收；② 回收阈值尚未触发（V8/媒体缓冲的 GC 不是实时的）。**两者都不改变结论：日常连续使用下，renderer 会一路涨到 3.5 GB 以上。**
2. **系统可用内存从 3918 MB 掉到 2436 MB**，其中 1477 MB 是本进程树的净增量。这台机器总量下，等于把整机可用余量吃掉了一半以上。
3. **CPU 24.25 s/min ≈ 单核 40% 常驻**（进程树累计，含浏览器/raster/解码/脚本）。这个数字在有播放时属正常量级，但**没有对照数据**说明其中多少来自 11 个用户脚本的 12 次/秒定时器。

## 4. 不能从这组数据得出的

| 想知道的 | 为什么不行 |
|---|---|
| JS Heap / DOM 节点实时值 | 实例以 `--remote-debugging-pipe` 启动，无 TCP 端口，外部无法 CDP |
| GPU 显存占用 | 需 `chrome://gpu` 或厂商工具 |
| 「最小化后 CPU 是否下降」 | **本时段未做最小化对照**（用户未最小化，或最小化时未标注）。这是 P0-2 的验证判据，尚未实测 |
| 各脚本的独立贡献 | 需要注入/不注入 A/B |
| 首屏耗时 / FCP / 资源体积 | 需 CDP timeline |
| 增长是否「无上限」 | 10.8 分钟太短。要判定必须 30 分钟以上并观察是否出现平台期 |
